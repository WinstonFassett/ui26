---
title: Using ui26 themes in Starlight
description: How to wire ui26's multi-theme system into a Starlight docs site, and the integration quirks you will hit.
---

ui26 themes use compound `data-theme` values (`editorial`, `editorial-dark`, `tix-dark`, …). Starlight was built around literal `"light"` / `"dark"` values for that attribute. This guide documents what you have to bridge and why.

## Install the theme CSS

Add the all-themes bundle to your global stylesheet:

```css
@import './styles/themes/all-themes.css';
```

Then use the `ThemeProvider` + `theme-picker` components to set `data-theme` on `<html>` at runtime (see [Theme picker UI](/guides/theming#theme-picker-ui)).

## Required: bridge `--sl-color-white` and `--sl-color-black`

Starlight only reassigns these two primitives via `[data-theme='light']`. Because our compound theme values never literally equal `"light"` or `"dark"`, those vars stay stuck at their initial values — white and near-black — regardless of what theme is active. Headings, sidebar items, the mobile menu toggle, and the search modal all consume them.

Fix: remap them in your `starlight-overrides.css` on `:root` (or `:where(:root)`) so they follow your theme tokens instead of Starlight's toggle:

```css
:where(:root) {
  --sl-color-white: var(--foreground);
  --sl-color-black: var(--background);
  --sl-color-text: var(--foreground);
  --sl-color-text-accent: var(--accent);
  /* ... other --sl-color-* you need ... */
}
```

Since this is a single bridge on `:root`, it works for all compound theme values without any per-theme rules.

## Required: bridge other `--sl-color-*` vars

Same problem applies to all Starlight color vars. Map the full set you care about — backgrounds, sidebar, nav, hairlines, gray scale — onto your semantic tokens:

```css
:where(:root) {
  --sl-color-bg: var(--background);
  --sl-color-bg-sidebar: var(--background);
  --sl-color-bg-nav: var(--background);
  --sl-color-bg-inline-code: var(--card);
  --sl-color-bg-hover: var(--muted);
  --sl-color-hairline: var(--border);
  --sl-color-hairline-light: var(--border);
  --sl-color-hairline-shade: var(--border);
  --sl-color-gray-1: var(--foreground);
  --sl-color-gray-2: var(--muted-foreground);
  --sl-color-gray-3: var(--text-mute);
  --sl-color-gray-4: var(--border);
  --sl-color-gray-5: var(--muted);
  --sl-color-gray-6: var(--card);
  --sl-font: var(--font-sans);
  --sl-font-system: var(--font-sans);
  --sl-font-system-mono: var(--font-mono);
}
```

The full bridge used by the ui26 docs site lives in [`apps/docs/src/styles/starlight-overrides.css`](https://github.com/WinstonFassett/ui26/tree/main/apps/docs/src/styles/starlight-overrides.css) — copy and adapt it.

## If you have a logo: replace Starlight's light/dark swap

Starlight's built-in logo swap uses `dark:sl-hidden` / `light:sl-hidden` utility classes, which only match literal `"dark"` / `"light"` `data-theme` values. With compound values both logos render simultaneously.

Fix: skip Starlight's logo config and render your own logo in a custom `Header` override using `[data-theme$="-dark"]` to select dark themes:

```css
/* Show dark logo when theme name ends in "-dark" */
[data-theme$="-dark"] .logo-light { display: none; }
:not([data-theme$="-dark"]) .logo-dark  { display: none; }
```

Or handle it in JS/React by reading `document.documentElement.dataset.theme`.

## Theme-specific fonts: repeat vars in dark blocks

If your theme defines `--font-sans`, `--font-serif`, or `--font-mono` on the light block, **also define them on the dark block**. The dark block only overrides what you declare — it doesn't inherit from the light block. Without this, toggling to dark causes font vars to fall through to `:root` (where they may be undefined or system defaults), causing a visible font switch.

```css
[data-theme="my-theme"] {
  --font-serif: "MySerif", ui-serif, Georgia, serif;
  /* ... */
}

[data-theme="my-theme-dark"] {
  /* Must repeat even though the value is the same */
  --font-serif: "MySerif", ui-serif, Georgia, serif;
  /* ... dark-specific tokens ... */
}
```

## Import order matters

Your `starlight-overrides.css` must import **after** the theme CSS so your bridge values override Starlight's defaults, not the other way around.
